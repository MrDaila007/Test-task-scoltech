# Джиттер выдачи телеметрии — x86_64

Требование: период выдачи телеметрии выдерживается с джиттером не более 1 мс.

## Методика

- **Что меряется.** Для каждого кадра периодической телеметрии — `|t_send − deadline|`. `t_send` берётся по `CLOCK_MONOTONIC` непосредственно перед `sendto()`, `deadline` — точка сетки `k · period`, к которой относится кадр. Кадры, отправленные при активном отказе линии F4, исключаются: их задержка — это внесённый отказ, а не джиттер.
- **Как держится период.** Один поток: `ppoll()` до абсолютного дедлайна. Опционально — активное ожидание последние `spin_us`. Предварительно `mlockall`.
- **Прогон.** 60 с в режиме реального времени, release-сборка, `scripts/measure_jitter.sh <idle|load> 60 <spin_us>`. Исходные отчёты лежат рядом в JSON.

## Условия

| | |
|---|---|
| CPU | Intel Core i7-10700F, 8 ядер / 16 потоков |
| ОС | Ubuntu 22.04, ядро 6.8.0-138-generic, `PREEMPT_DYNAMIC` (не PREEMPT_RT) |
| Governor | `powersave` |
| `SCHED_FIFO` | **нет**: `EPERM`, у процесса нет `CAP_SYS_NICE` (`ulimit -r = 0`) |
| `mlockall` | да |
| Нагрузка `load` | 16 процессов с активным циклом — по одному на каждый логический CPU |

## Выводы

1. **В простое требование выполняется с запасом в 3 раза** без каких-либо привилегий: максимум 0,31 мс. Активное ожидание 200 мкс снижает максимум до 0,15 мс ценой примерно 1 % одного ядра: 200 мкс на каждые 20 мс периода ATTITUDE.
2. **Когда все ядра заняты процессами того же приоритета, требование не выполняется:** максимум 5 мс. Планировщик CFS вытесняет поток выдачи. Это ограничение ОС, а не кода. На нагруженной машине нужен `SCHED_FIFO`: `sudo setcap cap_sys_nice+ep fc_stub`, `rtprio` в `limits.conf` или `docker --cap-add SYS_NICE`. Заглушка сама пытается его включить и предупреждает, если нельзя. Этот вариант здесь **не измерен**: прав нет.
3. **Кадры с общим дедлайном уходят последовательно** (HEARTBEAT → ATTITUDE → POSITION → BATTERY). Поэтому медиана у поздних потоков на 50–100 мкс выше: это время кодирования и отправки предыдущих кадров. Для бюджета 1 мс несущественно.
4. **Тайминги на целевом вычислителе здесь не доказываются.** На Jetson Orin Nano Super замер не выполнялся (NOT RUN), железа нет. Рекомендуемые условия для замера там: `nvpmodel` в режиме MAXN SUPER, `jetson_clocks`, ядро PREEMPT_RT из JetPack 6 и `SCHED_FIFO`. Команда та же: `scripts/measure_jitter.sh load 60 0`.
