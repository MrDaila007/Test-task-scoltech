# Джиттер выдачи телеметрии, x86_64

Требование: период выдачи телеметрии выдерживается с джиттером не более 1 мс.

## Методика

- **Что меряется.** Для каждого кадра периодической телеметрии считается `|t_send − deadline|`. `t_send` берётся по `CLOCK_MONOTONIC` непосредственно перед `sendto()`, `deadline` это точка сетки `k · period`, к которой относится кадр. Кадры, отправленные при активном отказе линии F4, исключаются: их задержка вызвана внесённым отказом, а не джиттером.
- **Как держится период.** Поток один: `ppoll()` до абсолютного дедлайна, при желании активное ожидание последние `spin_us`. Перед стартом вызывается `mlockall`.
- **Прогон.** 60 с в режиме реального времени, release-сборка, `scripts/measure_jitter.sh <idle|load> 60 <spin_us>`. Исходные отчёты в JSON лежат рядом.

## Условия

| | |
|---|---|
| CPU | Intel Core i7-10700F, 8 ядер / 16 потоков |
| ОС | Ubuntu 22.04, ядро 6.8.0-138-generic, `PREEMPT_DYNAMIC` (не PREEMPT_RT) |
| Governor | `powersave` |
| `SCHED_FIFO` | нет: `EPERM`, у процесса нет `CAP_SYS_NICE` (`ulimit -r = 0`) |
| `mlockall` | да |
| Нагрузка `load` | 16 процессов с активным циклом, по одному на каждый логический CPU |

## Выводы

1. В простое требование выполняется с запасом в 3 раза и без привилегий: максимум 0,31 мс. Активное ожидание 200 мкс снижает максимум до 0,15 мс и стоит примерно 1 % одного ядра (200 мкс на каждые 20 мс периода ATTITUDE).
2. Когда все ядра заняты процессами того же приоритета, требование не выполняется: максимум 5 мс. Планировщик CFS вытесняет поток выдачи, это ограничение ОС, а не кода. На нагруженной машине нужен `SCHED_FIFO`: `sudo setcap cap_sys_nice+ep fc_stub`, `rtprio` в `limits.conf` или `docker --cap-add SYS_NICE`. Заглушка сама пытается его включить и предупреждает, если не может. С `SCHED_FIFO` здесь замер не делался, прав нет.
3. Кадры с общим дедлайном уходят по очереди (HEARTBEAT → ATTITUDE → POSITION → BATTERY). Поэтому медиана у поздних потоков на 50-100 мкс выше: столько занимают кодирование и отправка предыдущих кадров. Для бюджета 1 мс это несущественно.
4. Тайминги на целевом вычислителе этот замер не доказывает. На Jetson Orin Nano Super замер не выполнялся (NOT RUN), железа нет. Для замера там рекомендуются `nvpmodel` в режиме MAXN SUPER, `jetson_clocks`, ядро PREEMPT_RT из JetPack 6 и `SCHED_FIFO`. Команда та же: `scripts/measure_jitter.sh load 60 0`.
